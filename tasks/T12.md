## Field host integration

`FieldWorld` (new `tantalus-game/src/field/world.rs`) owns actor state (positions, movement, turns, animations, jumps), windows, inventory, gil, party membership and stats, timers, field names, encounter and field/world transition queues, script/caller/shared-script request state, system variables/lists, object members, and deterministic synthetic randomness. `FieldHost` (`field/host.rs`) implements `LegacyEventHost` over it: `apply` folds host events into the world (walk/walk-toward/move/exit/teleport/delete, animation play/stop, turns, setup/progress jump with the reference JUMP3 interpolation, windows, items/gil with reference clamping, field name, timer, party menu, encounters, transitions, script/caller/shared-script requests, object initialization and UID mapping) and every trait query answers from that world; reads the world cannot back (BGI tables, atan, custom variables) fail with explicit `UnknownContent` errors. `FieldScene::step` plus `FieldWorld::advance` plus a fresh `FieldHost` per tick is the directed execution loop. Six integration tests in `tantalus-game/tests/field_host.rs` verify walk-then-wait resolution, window waits released by the director, gil/item accounting, encounter capture, jump interpolation to the destination, and explicit unknown-read failures. `SetupJump` now ends its step so a following `JUMP3` observes applied jump state (the reference's immediate state updates are modeled by the apply boundary); the analogous `PlayAnimation`/`WAITANIM` same-step visibility question is flagged for Claude in the mailbox.

## Real-execution probe

`tantalusctl assets inspect-bundle --field-execute <name>.eb [--ticks N]` decodes a real archive, registers each entry's first function as one `FieldDirector` scene entry (multi-function orchestration is host-owned and out of probe scope), and steps the director, reporting operations, completions, final VM states, and the first error. Evidence: `audit/field-execution.json`. Save/restore now resumes recorded VM positions through `EventVm::resume` (landed from Claude); VM variables and instruction budgets still start fresh on resume.

## Save/reload snapshots

`FieldSnapshot` (`tantalus-game/src/field/snapshot.rs`) is the versioned native save envelope for the current slice: `FieldWorld` state plus per-entry program source bytes and observed VM state (pc, status, wait state), with checked JSON round trips (`format` rejects unknown versions, missing program sources are explicit errors). `restore_scene` rebuilds the scene and world exactly; entries whose saved pc was past the entry point carry `resumed_from_start` and restart their programs until `EventVm::resume` (requested from Claude) applies the recorded position. The restart re-application of committed events is documented in the round-trip test (gil and items re-apply); the battle reward ledger already prevents double reward commits across restarts.

## Encounter coordination

`EncounterCoordinator` (`tantalus-game/src/battle/coordinator.rs`) owns at most one active encounter: `begin` rejects a second battle while one runs, `advance` forwards ticks and commands to the `CombatRuleset` and surfaces the outcome, and `finish` returns the request for field-return bookkeeping. `WorldGameServices` implements `GameServices` over `FieldWorld`: deterministic randomness from the world generator, and exactly-once reward commits — the first commit of a nonzero `resolution_id` applies gil with reference clamping and records the bundle, while duplicate commits are accepted and ignored so retries cannot double-apply. The `encounter_loop` integration test runs the full chain: a field `ENCOUNT` program queues the request, the coordinator begins a battle, attack commands run it to `Victory`, rewards land in world gil exactly once (a forced duplicate commit changes nothing), and `finish` releases the coordinator. Reward item grants still need a `ContentId`-to-legacy-item mapping before real content; experience is recorded but not yet applied to characters.

## Packaged native loop

`FieldDirector` (`tantalus-game/src/field/director.rs`) bundles the loop: `FieldScene` + `FieldWorld` + `EncounterCoordinator` + program sources + tick clock. `step` runs the field through `FieldHost`, advances the world, and drains encounter requests; `begin_battle`/`advance_battle`/`finish_battle` run the caller-resolved battle through the embedded coordinator with `WorldGameServices`; `save`/`restore` round trip the whole director through `FieldSnapshot` (an interrupted battle restarts from its encounter, per the restart semantics). The `native_loop` integration test proves the chain on synthetic programs: gil grant + async window + `ENCOUNT` -> entry completes (the reference jumps to battle) -> battle runs to `Victory` -> rewards commit once (gil 120) -> save/JSON/restore -> the restored director's world matches exactly and keeps stepping (documented restart re-application: the gil grant re-applies to 220, the battle reward does not). Running this loop on the real imported field's decoded programs is the remaining T12 gate; real gameplay parity remains unverified.

## Implementation approach

Reuse the headless simulation and public navigation/game services. `ScenarioRunner` reads bounded JSON, converts steps into ordered button transitions, advances the simulation, moves the field actor through BGI, checks expected state, and returns a serializable presentation/report.
