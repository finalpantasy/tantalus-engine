## Field host integration

`FieldWorld` (new `tantalus-game/src/field/world.rs`) owns actor state (positions, movement, turns, animations, jumps), windows, inventory, gil, party membership and stats, timers, field names, encounter and field/world transition queues, script/caller/shared-script request state, system variables/lists, object members, and deterministic synthetic randomness. `FieldHost` (`field/host.rs`) implements `LegacyEventHost` over it: `apply` folds host events into the world (walk/walk-toward/move/exit/teleport/delete, animation play/stop, turns, setup/progress jump with the reference JUMP3 interpolation, windows, items/gil with reference clamping, field name, timer, party menu, encounters, transitions, script/caller/shared-script requests, object initialization and UID mapping) and every trait query answers from that world; reads the world cannot back (BGI tables, atan, custom variables) fail with explicit `UnknownContent` errors. `FieldScene::step` plus `FieldWorld::advance` plus a fresh `FieldHost` per tick is the directed execution loop. Six integration tests in `tantalus-game/tests/field_host.rs` verify walk-then-wait resolution, window waits released by the director, gil/item accounting, encounter capture, jump interpolation to the destination, and explicit unknown-read failures. `SetupJump` now ends its step so a following `JUMP3` observes applied jump state (the reference's immediate state updates are modeled by the apply boundary); the analogous `PlayAnimation`/`WAITANIM` same-step visibility question is flagged for Claude in the mailbox.

## Map-100 stall root cause

Disassembly of the stall (entry 0 tag 1, offsets 483-534): the script waits `while SyncCinematic != 0`, then re-plays the cinematic unless `(sysvar15 & 127) == 17`. The pinned `FF9FieldFMVSync` never returns 17 (16/0/1 by status), and our auto-play movie finishes instantly (no frame counts), reaching status 8 where sync()==1 — so the wait spins forever. Movie frame counts are now wired end to end (a serde-skipped `FmvFrameCounts` provider on `FieldWorld`, used by `DispatchCinematic`; `tantalus-trace chain --game-data` builds it from the Ogg scan over the install's `StreamingAssets/ma/FMV*.bytes`). FMV005 (the map-100 arrival movie, script-init via `Cinematic(0, 261, 1)` = disc 1 number 5) measures 1003 frames / 66.9s (`real_fmv005_has_a_measurable_frame_count`). Corrected stall model: the stalled VM is entry 0's tag-1 loop parked at `CloseWindow`, which spins until another entry sets Map bit 231 (the invoke flag) — so the true blocker is the street sequencer entry, not the FMV. Layered diagnosis: entry 5 tag 1 is the stage machine (Map byte 24 switch, advanced via bit 231); bit 231 is set by scene actors including entry 2 and entry 19; entry 2 tag 1 (513@172) waits for Map byte 26 to reach 0; byte 26 is set to 2 by the scene director entry 19 (offset 287) and decremented by finishing walkers; at the stall byte 26 = 1, so one walker never finished — likely an `ActorMovement` wait on a party member that entry 19 itself removes (`RemoveParty` 0-3 at offsets 311-320). The next diagnostic is a watch on byte 26's decrement sites at runtime (tantalus-trace; Claude's lane).

## Save/reload snapshots

`FieldSnapshot` (`tantalus-game/src/field/snapshot.rs`) is the versioned native save envelope for the current slice: `FieldWorld` state plus per-entry program source bytes and observed VM state (pc, status, wait state), with checked JSON round trips (`format` rejects unknown versions, missing program sources are explicit errors). `restore_scene` rebuilds the scene and world exactly; entries whose saved pc was past the entry point carry `resumed_from_start` and restart their programs until `EventVm::resume` (requested from Claude) applies the recorded position. ## Encounter coordination

`EncounterCoordinator` (`tantalus-game/src/battle/coordinator.rs`) owns at most one active encounter: `begin` rejects a second battle while one runs, `advance` forwards ticks and commands to the `CombatRuleset` and surfaces the outcome, and `finish` returns the request for field-return bookkeeping. `WorldGameServices` implements `GameServices` over `FieldWorld`: deterministic randomness from the world generator, and exactly-once reward commits — the first commit of a nonzero `resolution_id` applies gil with reference clamping and records the bundle, while duplicate commits are accepted and ignored so retries cannot double-apply. The `encounter_loop` integration test runs the full chain: a field `ENCOUNT` program queues the request, the coordinator begins a battle, attack commands run it to `Victory`, rewards land in world gil exactly once (a forced duplicate commit changes nothing), and `finish` releases the coordinator.

## Reward experience levels characters through the growth provider

`commit_rewards` also grants battle experience to every party member via `FieldWorld::apply_experience` (`crates/tantalus-game/src/field/world.rs`). The world accumulates per-character totals in `character_exp` and resolves levels through a runtime `level_growth` provider (`LevelGrowth = Arc<dyn Fn(i32, u64) -> Option<CharacterStats>>`): find the highest level whose cumulative experience is at or below the total (minimum level 1, capped at the table), build stats from the vanilla `BaseStats.csv` + `Leveling.csv` tables, and on level-up add the max-HP/max-MP **delta** to current values, matching the reference's level-up behavior (a direct replace was found to wipe the delta; the merged stats are constructed explicitly). Character stats and experience round trip through `FieldSnapshot`. The chain (`tantalus-trace chain`) wires the real CSV tables into the provider. v1 documented deviation: experience is granted in full to each party member — no split rule.

## Reference EXP split replaces the v1 full-grant rule

`RewardBundle` now carries `shares: Option<BTreeMap<i32, u64>>` — per-character experience awards. When `Some`, `commit_rewards` grants only the listed characters; when `None`, the v1 fallback (full grant to every party member) remains for rulesets that predate the split. `battle::split_experience` implements the reference distribution (`BattleResultUI.AnalyzeArgument`, pinned `BattleResultUI.cs:514`): each eligible line receives `total / eligible_count`, integer division, remainder lost; no eligible line produces an empty map, which callers wrap in `Some` so a battle that paid nobody does not fall back. `FieldWorld::exp_eligible` is the v2 world-side eligibility (character has stats and current HP > 0); status-based reward disabling (Petrify/Virus/Zombie) and the `member_flag` participation bit are not yet modeled in `FieldWorld`. Claude's B8 `rewards.rs` remains the authoritative rich model (member_flag, DisableRewards, caps, level-up arithmetic); this bridge is the commit-path contract those awards flow through once the battle engine emits `shares`. Tests cover the remainder-lost rule, dead-member exclusion, empty-share suppression of the fallback, and end-to-end application.

## Shop bridge runs legacy trade rules against field state

`field::shop` is the transaction boundary between Claude's G9/G4 legacy shop rules and the field world. `inventory_from_world` snapshots the script-facing item map into a legacy `Inventory` (skipping keys that are not regular legacy ids — negative, above `u16`, or the `NoItem` sentinel 255 — and clamping to the 99 stack cap); `apply_inventory_to_world` writes slots back, dropping emptied stacks and leaving non-shop-managed keys untouched. `with_shop_inventory(world, trade)` runs the caller's trade closure against the view and commits item map + gil (capped at the reference 9,999,999) **only when the closure returns `Ok`** — a failed buy leaves the world byte-identical. Key-item obtained/used sets are not modeled in field state and stay caller-managed. Tests cover a committing buy (unrelated stacks survive), a rejected trade changing nothing, and a sell that empties a stack while capping gil, plus the sentinel/clamp round trip. ## Ability AP learning lands in world state

`FieldWorld` now carries per-character ability progress (`ability_pa`: character -> ability -> AP toward max, the reference `player.pa`) and a denormalized `learned_abilities` set, both serialized with `#[serde(default)]` and included in `PartialEq`. `FieldWorld::apply_ap` is the per-ability primitive of `AddAp` (`BattleResultUI.cs:561-587`): the caller loops the character's equipped learnable abilities as the result screen does; the primitive skips abilities with no AP goal or already learned, learns (sets to max) when `cur + amount >= max`, and otherwise accumulates, returning true exactly on learning. ## Packaged native loop

`FieldDirector` (`tantalus-game/src/field/director.rs`) bundles the loop: `FieldScene` + `FieldWorld` + `EncounterCoordinator` + program sources + tick clock. `step` runs the field through `FieldHost`, advances the world, and drains encounter requests; `begin_battle`/`advance_battle`/`finish_battle` run the caller-resolved battle through the embedded coordinator with `WorldGameServices`; `save`/`restore` round trip the whole director through `FieldSnapshot` (an interrupted battle restarts from its encounter, per the restart semantics). The `native_loop` integration test proves the chain on synthetic programs: gil grant + async window + `ENCOUNT` -> entry completes (the reference jumps to battle) -> battle runs to `Victory` -> rewards commit once (gil 120) -> save/JSON/restore -> the restored director's world matches exactly and keeps stepping (documented restart re-application: the gil grant re-applies to 220, the battle reward does not). Running this loop on the real imported field's decoded programs is the remaining T12 gate; real gameplay parity remains unverified.
